## CI parity (task item 3, last bullet)

Compared `.github/workflows/verify.yml`'s dedicated `Secret scan` step against what `secret-scan-branch.sh` does when it runs inside the same job's later `Run verification` step (`./scripts/run-verify.sh`, `RALPH_VERIFY_SCOPE: full`):

- **Range**: CI's dedicated step computes `base="$(git merge-base HEAD "origin/${GITHUB_BASE_REF}")"` unconditionally (relies on `actions/checkout`'s `fetch-depth: 0` to guarantee `origin/${GITHUB_BASE_REF}` exists). `GITHUB_BASE_REF` is set automatically by GitHub Actions for `pull_request` events, so `secret-scan-branch.sh`'s own base resolution (`GITHUB_BASE_REF` first, then prefer `refs/remotes/origin/$base_name`) lands on the identical `origin/${GITHUB_BASE_REF}` and the identical `merge-base..HEAD` range. Same range, both steps.
- **Allowlist**: CI's dedicated step calls `secret-scan.sh --range` directly, which defaults to reading `$repo_root/.gitallowed` from the checked-out worktree (`secret-scan.sh:18`). `secret-scan-branch.sh` instead explicitly reads `git show HEAD:.gitallowed`. In a normal CI checkout these are the same content (the worktree has no uncommitted diff from `HEAD`); the two approaches only diverge locally, where a developer might have an uncommitted `.gitallowed` edit — which is the intended divergence per AC-2c and the plan's design decision ("CI が読まないので無視し"). No parity gap.
- **Duplication, not a gap**: because `secret-scan-branch.sh` resolves to the same range and (in CI) the same allowlist content, CI now runs the same range scan twice per PR — once in the dedicated step, once inside `run-verify.sh`'s `Run verification` step. Since GitHub Actions steps stop the job on first failure by default, the dedicated step would already fail the job before `Run verification` runs, so the second scan inside `run-verify.sh` only ever executes when the first has already passed. This matches the self-review's own "Coverage gaps" note (duplicated work, not a defect); I independently re-derived the same conclusion by reading both scripts.
- **No case found where a local strict-clean run could still fail in CI, or vice versa**, under the conditions actually reachable by following the `/pr` skill in this repo (an `origin/main` ref that exists and nothing overriding `GITHUB_BASE_REF`/`RALPH_XREVIEW_BASE`) — consistent with the self-review's own reachability analysis (finding 2's "reachable by an agent... is empty").
