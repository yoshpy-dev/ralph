### The two directions the lane asked about

Misreading a network or API retry as a usage limit (a wrong `usage_limited` item steers the director to wait or switch accounts): no defect found. Each of these has to hold at once before `UsageLimitScreen` says true for a retry screen:

1. `ClassifyResumeScreen` says waiting (empty input box, a waiting sentence in the last block, the candidate, or the footer).
2. The last block above the input box holds both `Retrying in` and `attempt`. A working claude seat normally draws its spinner block last, so a reply or tool output that quotes these words is not in that place (not checked against a live screen); an idle seat usually ends with the `Worked for` status line, which holds neither. A final reply that quotes the retry line and a limit sentence with a glyph, with no status line after it, would still pass 2 and needs 3 and 4 as well; the waiting reading of such a reply already existed before this diff.
3. A block of the current turn (after the last `❯` block) holds a glyph, white space, a marked usage limit sentence, and later `resets <time>`.
4. The retry block holds `(<time>)` with that same time.

The network retry line the repo knows (`✻ Can't reach the… · Retrying in 4s · attempt 13/300`, evidence 2026-11-07 section 3) has no parenthesized time, so condition 4 fails for it whatever the turn holds. The test table pins the shapes around it: the retry alone, a limit before the last prompt, a limit mid-reply, no space after the glyph, a quoted limit with a network retry, a differing time, no prompt on screen and a differing time, no reset time, empty time, a retry that is not the last block, `Waiting for API response`, a retry without `attempt`, and codex. Every miss I could construct falls to the stall ALERT (the old behavior), not to a `usage_limited` item. The `(<time>)` equals reset time premise rests on one screen (L5, and the tech-debt row added); the plan states that.

Anything that could make resume type into a seat: no new path. `resumeLook` still returns `ResumeOutcomeWaiting` for every case that the new code changes, and `resumeOne` returns before the pane lock, `resumeSubmit`, and the `resumed` event whenever `outcome != ""`. The new calls (`resumeWorkingReason`, the `UsageLimitScreen` call in the waiting branch) only read. The look under the lock runs `resumeWorkingReason` too when the seat turned to working, which adds one read and still skips. Stopped and enter-only screens are not touched.
