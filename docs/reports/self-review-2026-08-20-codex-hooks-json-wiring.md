## Targeted verification (checks requested in the handoff)

**(a) Schema validator vs the official shape** — matches the shape the evidence records (`hooks` → event keys → matcher-group arrays → `{type:"command", command:<string>}`), and each level is asserted with its own finding: non-array event value, non-object group, missing/non-array `hooks`, non-object handler, missing-or-wrong `type`, missing `command`, non-string `command` (with `array` spelled out rather than `[]interface {}`), empty `command`. Finding strings carry the exact JSON path (`PostToolUse[0].hooks[0]`), which is the actionable part. All four negative cases the plan requires have tests. No finding filed.

**(b) Inverted contract, fail-open/fail-noisy symmetry** — no fail-open found. Every I/O error path warns rather than skipping: a non-`NotExist` read error on hooks.json becomes a finding instead of being swallowed, matching config.toml's own handling. Findings accumulate rather than short-circuiting on the first defect, so one run shows the operator every problem (`[features] hooks = false` + dual representation + schema defects together). The deliberate asymmetries are: absent `config.toml` early-returns before hooks.json is ever inspected (defensible — the whole `.codex/` tree is missing), and dual representation dropped from `fail` to `warn` (stated in the plan's risk register as a migration-noise decision). The one contract gap is documentation, not code: M1. Note that only `PostToolUse` counts toward `dispatcherRouted`, so a project wiring some other event through the dispatcher still warns — correct for today's single-event distribution, worth revisiting when a second event ships.

**(c) Shipped command string vs the live-fire evidence** — byte-identical. `.codex/hooks.json` decodes to `"$(git rev-parse --show-toplevel)/.claude/hooks/ralph-dispatch.sh" PostToolUse`, character-for-character the form in `docs/evidence/codex-hooks-livefire-slice1-2026-08-20.md:8`; matcher `Edit|Write|MultiEdit|apply_patch` matches `:7`. Root and `templates/base/` copies are identical (`diff` clean), and the PR adds `check_codex_hooks_json_byte_identical` so a future one-sided edit fails closed. The Go fixture `validHooksJSON` reproduces the same command string, so a change to the shipped form surfaces in the unit tests too.

**(d) Can the new shell checks false-pass or false-fail?** — command extraction is real jq parsing (`.hooks.PostToolUse // [] | .[] | (.hooks // [])[] | select(.type == "command") | .command`), not a grep approximation, so the `description` field cannot be mistaken for a command; the earlier false positive is properly fixed by scoping to jq-extracted strings on the JSON side and to `command =` assignment lines on the TOML side (comment lines start with `#`, so the prose mentions of `ralph-dispatch.sh` and the secret-guard scripts cannot match). `jq` is required up front (`:27-28`), so its absence fails loudly rather than as a bogus "not valid JSON". Two residues filed: M3 (spaced-table evasion) and L5 (vacuous silent guard); L4 records the assertion that was dropped in the swap.

**(e/f) Comment/doc accuracy and shipped-content purity** — H1, M1, M2, M4, M5 are this dimension. On purity specifically: no leak found in shipped content — `templates/base/.codex/**` and `templates/base/docs/recipes/codex-setup.md` contain no plan slug, no `docs/evidence`/`docs/plans` path, no dated report filename, no `codex-cli 0.147.0` version, and no `2026-08-*` date. The config.toml comment deliberately says "on the codex-cli release this was verified against" instead of pinning the version, which is the right instinct for shipped text. The one near-miss is L3 (`tests/test-hook-wiring.sh` named in shipped content). `.codex/AGENTS.override.md:56` still describes project-level hook requirements as "`[features] hooks = true` + project trust" without the new hook-approval step — untouched by this PR and adjacent to M1; flagging it here rather than as its own row since it belongs to the same one-story fix.
