## Positive notes

- Stat-then-open matches `readCodexUserConfig` line for line: the same `IsRegular` test and the same `not a regular file` text. The synthetic error goes through the existing `!scan.Opened` → `couldNotRead` path, so no new Detail clause and no new severity rule were needed. `shellAliasUnreadableReason` passes the plain error's text through unchanged.
- A side benefit follows from the code, though it was not tested here: a candidate symlinked to a character device such as `/dev/urandom` or `/dev/zero` is also rejected before open. The old code would have read `/dev/urandom` effectively without end, because newlines keep every line under the 1 MiB cap.
- The FIFO test cleanup order is correct. `t.Cleanup(unblockFIFOOpen)` is registered after `t.TempDir()`, so it runs first (LIFO) while the FIFO still exists. `O_WRONLY|O_NONBLOCK` never blocks, and ENXIO (no reader) is ignored. The leaked goroutine in a red run never touches `t`, so it cannot panic after the test ends. The channel has a buffer of 1, so its send never blocks.
- The AC-5b/5c/5d fixtures leave nothing at the lexically cleaned location, so their `warn` assertions fail if the candidates go back to `filepath.Join` (the implementer's red/green). My own FIFO mutation confirmed that the FIFO tests go red with the check removed.
- The helper names (`shellAliasJoinRaw`, `shellAliasRawParent`, `shellAliasZdotdirBase`) follow the file's `shellAlias*` prefix and are easy to grep. `cwd, _ := os.Getwd()` discards the error on purpose, and the doc says so (Go's `Getwd` returns `""` on error).
- Security: the diff adds no output beyond paths. Alias values, file contents, and flag values are still never printed, and the flag labels still come from a fixed set.

## Answers to the focus points

1. Checked, no issue. The only `os.Open` in the check (`scanShellAliasFile`) now comes after an `os.Stat` + `IsRegular`. The candidate walk uses `os.Stat` (which never opens) and `filepath.EvalSymlinks` (`Lstat`/`Readlink` only). Both stats follow symlinks, so they agree. If the file vanishes between the two stats, the scan reports `could not read: <file> (no such file or directory)`, the same text `os.Open` produced before the change, so nothing new can mislead. With a FIFO, `scannedOK` excludes it, the clause reads `scanned 0 shell rc file(s)` or lists only the real files, and `couldNotRead` names the FIFO, so the counts stay truthful.
2. LOW-1 (root parent `""`, which also affects `HOME=/`) and LOW-2(c) (`JoinRaw` with two trailing separators). The other inputs are fine: `/` → `/.zshrc`; `.` → `<cwd>/./.zshrc`; `..` → `<cwd>/../.zshrc`; `./rc` → `<cwd>/./rc/.zshrc`; `rc/` → `<cwd>/rc/.zshrc`; empty Cwd skips every relative form; Cwd `/` gives `/./.zshrc`. For `$HOME`-built candidates, `shellAliasRawParent` matches `filepath.Dir` except at the root.
3. Checked, acceptable. `filepath.EvalSymlinks` resolves each symlink as it walks and applies `..` to the resolved prefix, so dedup works on physical paths (the orchestrator's scratch test agrees). Display paths that keep `..` follow the file's existing rule that the Detail names the candidate, not the target. `~/proj/../.zshrc` is readable, and cleaning it would sometimes name the wrong file (see LOW-4 for why a test should pin this). Cosmetic, not counted: `ZDOTDIR=.` with cwd `$HOME` shows the finding as `~/./.zshrc`, because the `$ZDOTDIR` candidate comes first and wins dedup. An unsearchable `$HOME` is then listed twice, as `~/.` and as the absolute home path, because `seenDir` keys are raw strings. The absolute-path spelling of home itself predates this diff.
4. The tests are hermetic apart from LOW-6. The FIFO tests cannot hang the suite (confirmed: a red run takes 5 s per test, 16 s for the package). The test names say what they protect. The new `warn` assertions go red if the fix is reverted, but the display assertions do not pin the path (LOW-4). The AC-4 directory test is a real regression guard: it fails if `shellAliasRcCandidates` stops skipping directories, because `scanShellAliasFile` would then report the directory as `not a regular file`.
5. LOW-2 (the two very long lines, the rationale repeated in four places, `JoinRaw`'s overclaim) and LOW-3 (two doc comments missing the new field). The rest is accurate, and the real-zsh probe confirms the new `shellAliasRcCandidates` paragraph. The comments describe the code, not its history. The production comments added in this diff contain no finding ids. The test comments cite AC numbers, each followed by a description, which matches the file's existing `WC-2's other half` / `H1 fix` style.
6. Checked, no issue beyond the findings above. The names are consistent, the error handling is explicit (`Getwd` error discarded on purpose and documented), there are no unrelated changes and no debug output, and no alias value or file content is printed.
