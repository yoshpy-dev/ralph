## Objective

機能の org が出す PR について、どの commit をどの main の上でゲートに通したかを、ralph が台帳に記録する。leader は PR を出す前に main に rebase し、push する head で `ralph org gate` を打つ。gate は作業ツリーと rebase を確かめてから `./scripts/run-static-verify.sh` と `./scripts/run-test.sh` を走らせ、結果を `gate_passed` か `gate_failed` として、head と base の SHA と一緒に manifest に書く。

7c(次の PR)は、この記録を読んで「merge してよい順」(FR-8)を出す `ralph org merge-order`、`ralph doctor` の保護ブランチの warn、`ralph status` の保証の表示を入れる。

## Scope

- 新しい動詞 `ralph org gate --org-id <id>`
  - 打つのは機能の org の leader で、打つ場所は結びつきの worktree の中(サブディレクトリでもよい)。`--state-dir` と `--config` は他の動詞と同じに受け付ける
  - 走らせる前に次を確かめ、通らなければ何も記録せず、スクリプトも走らせずに終了コード 1 で断る。拒否の文は理由と次の手を 1 つ言う
    - 台帳に、その org の今の命の完全な結びつき(`ActiveFeature` が返し `Complete()`)があり、org が走っている(`RunningOrgs`)
    - 打った場所の worktree のルート(`git rev-parse --show-toplevel`)が結びつきの worktree と同じ(symlink を解いて比べる)。今のブランチ(`git branch --show-current`)が結びつきのブランチと同じ(detached HEAD は断る)
    - 作業ツリーがきれい: `git status --porcelain --untracked-files=all` が空(ignore されたファイルは数えない)
    - 既定のブランチが決まる(下の「base の決め方」)。base ref の先頭が HEAD の祖先(`git merge-base --is-ancestor`)。祖先でなければ「`git fetch origin <既定のブランチ>` と `git rebase <base ref>` のあとに打ち直す」と言う
    - worktree のルートに `scripts/run-static-verify.sh` と `scripts/run-test.sh` があり、実行できる
  - base の決め方: 既定のブランチは `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` の `origin/` を除いた名前。なければ `main`、それもなければ `master`(`refs/remotes/origin/<名前>` か `refs/heads/<名前>` のどちらかがあるもの)。base ref は `refs/remotes/origin/<名前>` があればそれ、なければ `refs/heads/<名前>`。記録する base の SHA は base ref の先頭(祖先の検査を通ったあとなので、HEAD と base ref の merge-base と同じ)。gate は fetch しない(ネットワークを使わない)
  - 走らせ方: worktree のルートで `./scripts/run-static-verify.sh`、通れば `./scripts/run-test.sh` を順に走らせる。環境は打った側のものから、名前が `RALPH_VERIFY_` か `HARNESS_VERIFY_` で始まる変数をすべて除き、`RALPH_VERIFY_SCOPE=full` を足して渡す(Design decisions の B9)。出力は台帳の下のログ(`<state-dir>/gates/<org_id>-<UTC の時刻>.log`)に書き、worktree を汚さない。manifest のロックはスクリプトを走らせている間は持たず、最後の記録のときだけ取る
  - 走らせたあとに、HEAD が走らせる前と同じか、作業ツリーがまだきれいかを確かめる
  - 記録: manifest に org 全体の event(seat_id は空)を 1 行足す。通れば `gate_passed`(Details は `head=<40 桁> base=<40 桁> base_ref=<ref> branch=<ブランチ> log=<ログのパス>`)、落ちれば `gate_failed`(`reason=static_failed|test_failed|head_moved|tree_changed` を先頭に、同じキーを続ける)。打った側の情報(`by=<USER> herdr_pane=<set|unset>`)も 7a の `plan_approved` と同じ形で足す。どちらも状態の event ではない(座席の状態を変えない)
  - 出力: 通れば stdout に `GATE: pass`、`HEAD: <40 桁>`、`BASE: <40 桁>` の 3 行(leader が RESULT のヘッダにそのまま写せる形)とログのパス、終了コード 0。落ちれば `GATE: fail`、理由、ログのパス、落ちたスクリプトの出力の最後の 20 行、終了コード 1
  - 6b の見張りの関門と 7a の承認の検査はかけない(gate は新しい自律の作業を始めない)
  - 中断(SIGINT・SIGTERM)されたら、子のスクリプトを止め、何も記録せずに終わる
- 見張り: `leaderActivityEventCount`(`internal/org/watch.go`)が `gate_passed` と `gate_failed` を leader の動きに数える。gate を走らせている間は manifest に event が増えないが、終わった時点で数える
- `scripts/run-verify.sh`(と `templates/base/scripts/run-verify.sh`、同じ中身): 1 回の実行の中で受け渡す 3 つのファイル(終了コードの `.harness/state/verify-exit-code`、言語の範囲の `.harness/state/verify-scope`、docs だけかの印 `.harness/state/non_docs_change`)を、実行ごとの一時ファイル(`mktemp`)に替える。同じ worktree で 2 つの検証が重なっても、片方の終了コードや範囲をもう片方が上書き・削除しない(B10)。終了コードのファイルが読めないときは成功とみなさず失敗にする。`.harness/state/verify-scope` は、実行の最後に一時ファイルから写して今までどおり残す(読む側のため)
- leader の雛形(`internal/org/prompts/leader.md` の「機能ごとの org」)の、reviewer が通したあとの順を変える
  1. `git fetch origin <既定のブランチ>`。HEAD が `origin/<既定のブランチ>` を含まなければ `git rebase origin/<既定のブランチ>`。衝突したら `git rebase --abort` し、implementer に rebase と衝突の解消を TASK で頼み(per-plan では `PLAN:` を付ける)、解消したら reviewer にレビューを頼み直す。fetch が失敗したら BLOCKED を escalate する
  2. `ralph org report` を打ち、report と reviewer のレポート(`docs/reports/` の下)をコミットする。続けて計画を archive し、計画の移動(スクリプトが書き換えたほかのファイルを含む)を別のコミットにする
  3. `./scripts/secret-scan-branch.sh --strict`(あれば)
  4. `ralph org gate --org-id {{ORG_ID}} --state-dir <台帳>`。数分かかるので、ツールの timeout を長くするか、バックグラウンドで走らせて終わりを待つ。拒否されたら文の次の手に従う。`GATE: fail` なら、まず `git revert --no-edit <archive のコミット>` で計画を `docs/plans/active/` に戻す(per-plan では、承認の記録は元のパスを指すので、戻さないと implementer への TASK が承認の検査で断られる。中身が承認した版と同じなら通る)。そのうえで implementer に直しを TASK で頼み、往復に戻り、reviewer が通したら 1 からやり直す(B11)
  5. implementer と reviewer を `ralph org stop` で止める
  6. HEAD が gate の `HEAD:` と同じことを確かめて push し、`gh pr create` で PR を作る。RESULT の escalate のヘッダに gate の `HEAD:` と `BASE:` を写し、EVIDENCE に PR の URL を書く
  7. worktree とブランチは残す。最後に disband する(今の手順のまま)
  - gate のあとにコミットを足さない。足したら gate を打ち直す
- reviewer の雛形(`internal/org/prompts/reviewer.md`): RESULT のヘッダに、検証した `HEAD:`(`git rev-parse HEAD`)と `BASE:`(`git merge-base HEAD <既定のブランチ>`。leader の TASK に指定があればそれ)を書く(仕様の「reviewer の結果には、検証した head と base の SHA を残す」)。ralph はこの 2 行を読まない。merge してよい順(7c)は台帳の `gate_passed` だけを使う
- 文書: `/org` skill の 4 面(動詞の表に `gate`、機能ごとの org の手順)、`docs/quality/quality-gates.md` と template の写し(82 行の「enforced mechanically ではない」の行に gate の記録を足す)、仕様 FR-7 の「7 段目の後半(7b)で決めたこと」、AGENTS.md の repo map(新しいファイル)、`docs/tech-debt/README.md`

## Non-goals

- 7c の項目: `ralph org merge-order`(FR-8 の merge してよい順)、`ralph doctor` の保護ブランチの warn、`ralph status` の保証の表示
- 結びつきのない org(`ralph org start <task>`、昇格した leader)の gate
- gate が fetch すること、PR を作ること、push すること
- reviewer に gate を打たせること(Design decisions の B3)
- gate のスクリプトやコマンドを設定で変えること(今の reviewer の雛形と同じく 2 つのスクリプトに固定する)
- leader が gate を打たずに PR を出すのを止めること。gate の記録がない PR は、7c の merge してよい順に出ないだけになる
- `GATE:`・`HEAD:`・`BASE:` のヘッダを `ralph org send` や `escalate` が検査すること

## Assumptions

- `ralph init` が出荷する `scripts/run-static-verify.sh` と `scripts/run-test.sh` は、`run-verify.sh` を呼ぶ薄い包みで、出力は `.harness/` と `docs/evidence/*.log` に書く。どちらも `templates/base/.gitignore` が ignore するので、ゲートを走らせても作業ツリーは汚れない(古い scaffold で ignore の行がない project では汚れ、gate は `tree_changed` で落ちる。拒否の文で知らせる)

- 台帳の `.harness/state/org/` は main worktree の下で、ignore されている(1 段目)

## Design decisions

critical forks は consult(consult-plan-stage7b)に聞いて自分で選んだ(ユーザーの指示「計画の分かれ目も自分で選ぶ」)。

- B1 7 段目の後半を 2 つの PR に分ける。7b(この計画)は gate と雛形で、ローカルの git とスクリプトだけで決まる。7c は merge してよい順・doctor・status で、`git ls-remote` と `gh` を呼ぶので seam と stub が要る。7a は internal/ で +6,035 行になり、cycle の上限は 2 なので、1 本にすると cross-review で詰まったときに戻しにくい
- B2 検証の記録は ralph の動詞が書く。仕様の FR-8 の「検証した base が今の main と一致する PR」は、検証の記録がなければ決められない。reviewer の RESULT の申告だけに頼ると、根拠が LLM の言葉になる。仕様の Security considerations(越権の防止は動詞の検証で強制する)と 7a の `plan_approved` の前例に合わせる。reviewer の RESULT の `HEAD:` と `BASE:` は仕様の字義どおり雛形に残すが、ralph は読まない。退けた案: 雛形の決まりだけで、merge してよい順が受信箱の本文を読む
- B3 gate を打つのは leader。reviewer と implementer の座席は台帳に書けない(`internal/org/permissions.go` の `codexWritableRootArgs` のコメント: manifest や他の座席の prompt を書き換えられるため)。reviewer に打たせると codex の座席では記録に失敗し、書けるようにすると 1 段目の決定を覆す
- B4 最後の gate は push する head で取る。review のあとに report と計画の archive のコミットが増えるので、review の時点の head は push する head と違う。差分が `docs/` の下だけなら検証済みとみなす規則は、規則が増え、docs を読むテストのある project で外れる。代わりにテストを 2 回(review と最後)走らせる
- B5 gate は rebase を求めるが fetch はしない。base ref の先頭が HEAD の祖先でなければ断る。fetch は leader の手順に置く(codex の workspace-write はネットワークを止めうるので、push と同じく失敗したら BLOCKED)。手元の `origin/<既定のブランチ>` が古いまま gate を通ると、記録の base は古い main になり、7c の merge してよい順で「rebase が要る」と出る
- B6 作業ツリーはきれいでなければ断る(例外を作らない)。ゲートのスクリプトの出力は ignore された場所に書かれ、gate のログは台帳の下に置くので、gate 自身は作業ツリーを汚さない。reviewer のレポートは leader が gate の前にコミットする。走らせたあとに HEAD が変わった、作業ツリーが汚れたなら、検証した中身が commit と一致しないので `gate_failed` にする
- B7 走らせる前の拒否は何も記録しない(7a の TASK の拒否と同じ)。スクリプトが落ちたときは `gate_failed` を記録する。同じ head で通ったあとに落ちたら(テストの揺れなど)、最新の記録が落ちたほうになり、7c の merge してよい順は最新の記録を読む
- B8 対象は結びつきのある org だけ。PR を作るのは機能の org の手順で、merge してよい順も結びつきのブランチで PR を引く
- B9(Codex plan advisory の指摘 1 で直した): gate は検証の範囲を固定する。`run-verify.sh` の `changed` の範囲は `RALPH_VERIFY_BASE` を差分の基点にするので、打った側の環境に `RALPH_VERIFY_BASE=HEAD` があると、きれいな作業ツリーは「変更なし」になり、言語の検証が走らないまま通る。`RALPH_VERIFY_PROJECT_ROOTS` も言語の検証の範囲を狭めうる。gate は `RALPH_VERIFY_` と `HARNESS_VERIFY_` で始まる変数をすべて除き、`RALPH_VERIFY_SCOPE=full` で走らせる。merge の前の検証なので、差分で範囲を狭めない。退けた案: `changed` のまま `RALPH_VERIFY_BASE` を記録する base の SHA に強制する(範囲の判定が `detect-changed-languages.sh` の規則に依り、狭めた分の根拠を記録に残せない)
- B10(Codex plan advisory の指摘 3 で直した): `run-verify.sh` は終了コードを `.harness/state/verify-exit-code` で受け渡し、読んだら消し、ファイルがなければ成功とみなす。同じ worktree で検証が重なると(バックグラウンドの gate の打ち直し、reviewer の検証)、片方の失敗をもう片方が上書きか削除して、gate が誤って `gate_passed` を書きうる。gate 同士の排他だけでは reviewer の検証と重なるのを防げないので、`run-verify.sh` の受け渡しのファイルを実行ごとの一時ファイルにし、ファイルが読めなければ失敗にする。退けた案: worktree ごとのロック(すべての検証の入口に入れる必要があり、止まった実行がロックを残す)
- B11(Codex plan advisory の指摘 2 で直した): 計画の archive のあとに gate が落ちたら、archive のコミットを revert してから implementer に直しを頼む。per-plan では、7a の承認の検査が承認の記録のパスに今のファイルがあることを求めるので、archive したままでは implementer への TASK が断られて止まる。revert は計画を同じ中身で元のパスに戻すので、承認の記録と全文のハッシュがそのまま合う。そのために、report のコミットと archive のコミットを分ける。退けた案: gate のあとに archive する(gate のあとにコミットが増え、B4 が崩れる)、承認の検査が archive 先のパスも読む(7a の検査の規則が増える)

## Acceptance criteria

## Risks and mitigations

- テストを 2 回走らせるので PR までの時間が延びる: 受け入れる(B4)。gate のログで時間を追える。gate は `full` の範囲で走るので、review の `changed` の範囲より長くなりうる(B9)
- `run-verify.sh` の変更が、出荷するすべての project の検証に効く: 受け渡しのファイルを一時ファイルに替えるだけで、出力と終了コードの意味は変えない。既存の shell のテストで確かめる。`.harness/state/verify-scope` を読む側のために、最後に写して残す
- 計画の archive を revert したあとの PR の履歴に、archive と revert のコミットが残る: 受け入れる(履歴を書き換えない)
- leader のツールの timeout で gate が切られる(Claude Code の Bash は既定 2 分、最大 10 分): 雛形に、timeout を長くするか、バックグラウンドで走らせて待つよう書く。切られたら何も記録されないので、打ち直せばよい。今の reviewer も同じスクリプトを直接打っている
- codex の leader の sandbox で、テストのキャッシュ(Go の GOCACHE など)や fetch がネットワークや writable root の外を求めて落ちる: 今の reviewer の座席と同じ条件。fetch の失敗は BLOCKED にする。実機で確かめられなければ tech-debt に書く
- 古い scaffold で `docs/evidence/*.log` が ignore されていない project は、gate が毎回 `tree_changed` で落ちる: 拒否の文に汚れたファイルを並べ、`.gitignore` に足すよう言う
- leader が gate を打たずに PR を出す: 止められない(Non-goals)。7c の merge してよい順に出ないので、人が気づける
- report を座席の stop の前に打つので、report に座席の stop が載らない: report は PR を出す前の台帳の写しと雛形に書く
- rebase で衝突したときに leader が自分で直す: 雛形で「leader はコードを直さず implementer に頼む」と書く

## Rollout or rollback notes

- release のノート: 新しいサブコマンド `ralph org gate`、manifest の新しい event `gate_passed` と `gate_failed`、台帳の下の新しいディレクトリ `gates/`(gate のログ)。機能の org の leader は、PR を出す前に main に rebase し、push する head で gate を打つ(review のテストと合わせて 2 回走る。gate は `full` の範囲)。7c で merge してよい順がこの記録を読む。`run-verify.sh` は、1 回の実行の中で受け渡すファイルを実行ごとの一時ファイルにした(同じ worktree で重ねて走らせても結果が混ざらない)。`ralph upgrade` が core のファイルとして差し替える
- revert すると gate の動詞と雛形の手順がなくなり、7a の動き(reviewer の GATE: pass で PR を出す)に戻る。台帳に残った `gate_*` の event は古い版では読まれない(seat_id の空の event は Roster が飛ばす。見張りの数え方からも外れる)。`gates/` のログは残るが、何も読まない
