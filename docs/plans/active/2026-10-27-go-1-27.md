## Objective

この repo では Go の版が 2 つある。`go.mod` の `go` の行は 1.25.8 で、CI(`.github/workflows/verify.yml`)と release(`.github/workflows/release.yml`)は `actions/setup-go` の `go-version-file: go.mod` でこの版を使う。メンテナの手元の既定は Homebrew の go 1.27.3 で、`GOTOOLCHAIN=auto` は新しいほうを使う。そのため、手元では静的検査を `GOTOOLCHAIN=go1.25.8` で回し、Go のテストを 2 つの版で回してきた。

この計画では `go.mod` の `go` の行を 1.27.3 に上げ、CI、release、手元を同じ版にする。上げると条件に当たる tech-debt の項目((j)、(k)、(l)、(n))も払う。

## Assumptions

- 手元の道具は計画の前に新しくした。golangci-lint は `brew upgrade golangci-lint` で 2.9.0(go1.26.0 製)から 2.15.0(go1.27.2 製)に(ユーザーの許可あり)。staticcheck は `~/go/bin` の v0.7.0(go1.26.0 製)が go 1.27.3 の標準ライブラリを読めない(「export data version 5 is greater than maximum supported version 2」)ので、`GOTOOLCHAIN=local go install honnef.co/go/tools/cmd/staticcheck@latest` で 2026.2.2(0.8.2、go1.27.3 製)に(許可の外。戻し方は `go install honnef.co/go/tools/cmd/staticcheck@v0.7.0`)
- 計画の前の確かめ: repo の写し(`git archive HEAD` を scratchpad に展開)で `go mod edit -go=1.27.3` のあと、`go mod tidy` は go.mod も go.sum も変えず、golangci-lint 2.15.0 は errcheck の 1 件だけ、staticcheck 2026.2.2 と `go vet ./...` は rc 0
- Go 1.27.3 の `signal.NotifyContext`(`$GOROOT/src/os/signal/signal.go:293-325`)は、`context.WithCancelCause` の上で、最初の signal で原因 `<signal> signal received` を付けて取り消し、`stop` は `cancel(nil)` と `signal.Stop` を呼ぶ。登録は `stop` まで残るので、後の signal も捕まえる。`gateSignalContext` との違いは、`stop` が goroutine の終わりを待たないことと、signal を渡さないと全 signal を受けることで、3 か所の呼び出しはどちらにも当たらない(届いた signal を読まず、いつも 3 つの signal を渡す)
- `actions/setup-go` は `go-version-file` の `go 1.27.3` を読んで 1.27.3 を入れる(CI で確かめる)
- 上げたあとは、go1.25.8 では build できない(`go.mod requires go >= 1.27.3`)。手元の Go のテストは 1 つの版で済む

## Design decisions

Critical forks: None(下の選択はどれも 1 slice の手戻りより安く戻せる)

- D1 go の行は `1.27.3`、`toolchain` の行は足さない: 手元(brew の 1.27.3)、CI、release を同じ版にするのが依頼の趣旨。`toolchain` の行は go の行と同じなら要らない。`1.27.0` にする案は、CI と release が 1.27.0 を入れて手元と patch がずれるので採らない。go の行は最低の版の指定なので、これだけでは手元の Go が上がったときのずれを防げない(D7)
- D7 版のずれはこの repo のテストで止める(Codex の計画助言、MEDIUM): `GOTOOLCHAIN=auto` では、brew が 1.27.4 に上がると手元は 1.27.4 を使い、CI と release は go.mod の 1.27.3 のままになる。検証の script(`scripts/run-static-verify.sh`、`run-test.sh`、`run-verify.sh`)に go.mod から導いた `GOTOOLCHAIN` を足す案は、その script が `templates/base/scripts/` から scaffold 先にも配られ、downstream の project の go の行(最低の版)に toolchain を固定してしまうので採らない。`go env -w GOTOOLCHAIN=...` は利用者の go.env を書き換えるので採らない。この repo だけが走らせる Go のテストで、版が違えば落とす。CI は setup-go が go.mod の版を入れるので通る
- D2 tech-debt (j) を払う: (j) の Trigger「go の行が 1.26 以上になること」をこの PR が満たす。`signal.NotifyContext` は `gateSignalContext` と同じ原因の文と取り消しを持つ(Assumptions)ので、置き換えは動きを変えない。残すと、`gateSignalContext` の「go.mod が 1.25.8 を許すので NotifyContext を使わない」という理由が嘘になる
- D3 `signalCauseContext` は `org_wait_director.go` に移す: gate が使わなくなると、使うのは `ralph org wait --inbox --director` だけになる。`org_gate.go` に残すと、gate のファイルに gate の使わない helper が残る。移すだけで中身は変えない
- D4 (k)・(l) も払い、(m) は持ち越す: (k) の Trigger は「そのテストの次の編集」、(l) は「`gateSignalContext` の次の編集」で、どちらもこの PR が当たる。(l) のテストは 2026-10-13 の probe がそのまま使える(HEAD で 10/10 通り、mutant で 10/10 落ちた)。(m) の Trigger は「チャネルの次の編集」か「窓を狙えるテスト」で、この PR はどちらにも当たらない
- D5 errcheck は `_ = <-done`: 受け取る値は使わず、goroutine の終わりを待つだけなので、捨てることを字で示す
- D6 split_test.go の fixture は直さない: 分割計画の本文の例で、テストは文字列として読むだけ
